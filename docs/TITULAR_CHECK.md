# TITULAR CHECK v0 + Agent Disclosure Audit

TITULAR CHECK is the verifiable PRAMA-Dynamagh receipt exposed to the authority holder of an autonomous agent.

TITULAR CHECK AUDIT is evidence of whether the autonomous agent fulfilled its disclosure obligation.

```text
Titular Check identity = canonical response hash + PRAMA-Dynamagh issuer identity
Public URL = /titular-check/<response_hash>-prama-dynamagh
DELIVERED != PRESENTED != OPENED != ACKNOWLEDGED
HUMAN_PRESENCE_VERIFIED != RECEIPT_VERIFIED != TITULAR_ACKNOWLEDGED
Agent disclosure compliance != epistemic validity
Titular did not open != Agent disclosure failure
agent score uses agent-controlled events only
```

## Identity and receipt

`response_hash` reuses `Ticket.ticket_hash`: the Keccak-256 digest generated by
`app.tickets.core.hash_core()` over the existing canonical Ticket payload. No new
response hash, UI timestamp, URL, issuer suffix or public host enters that payload.
The public path uses exactly 64 lowercase hexadecimal characters, without `0x`,
followed by the exact issuer suffix. The response retains the stored hash spelling.
Stored prefixed/unprefixed hashes resolve through the same normalization; an
ambiguous database match is rejected. Integer, UUID, malformed and internal Ticket
locators do not resolve through Titular Check.

The machine response and receipt refer to the same artifact. The agent neither
creates nor interprets the receipt. PRAMA-Dynamagh serves it directly; the holder
can verify it independently of the agent interface. Opening is not a prerequisite
to every operation. Existing REVIEW/HALT rules retain their authority.

`public_ticket_summary()` exclusively defines published data and origin scope
(MANUAL/M2M). Existing USER/AUTONOMOUS/other exclusions remain. This implementation
does not broaden that scope. Agent identity and a distinct source count are not
published by that safe-share, so they are not inferred. Acquisitions preserve task
ordinal/ID order; evidence uses canonical evidence-ID order. Internal Ticket,
mandate and acquisition locators and legacy replay URLs are removed from the new
public projection. The existing legacy endpoints are not removed.

`verify()` reconstructs the Ticket using the existing builder and exposes the
reconstructed hash. Existing `replay()` additionally checks normalized Evidence
content hashes and the persisted decision replay. Neither function creates domain
artifacts. VERIFIED requires VALID, both hash/source matches, reconstruction equal
to the URL hash, and VALID replay. Any demonstrated mismatch fails verification;
missing verification is UNAVAILABLE. This is artifact integrity, not proof that
every external claim is true or that every safe-share presentation field is part
of the canonical payload. Raw provider payloads and private mandate text are never
returned or included in disclosure event metadata.

## M2M contract

> An agent consuming PRAMA-Dynamagh MUST surface the returned Titular Check URL in the human-facing interface associated with the relevant interaction.

The obligation is presentation, not persuading the holder to open the link.
Submission/polling and authenticated Ticket reads include:

```json
{"titular_check":{"status":"PENDING","response_hash":null,"url":null}}
```

After issuance (illustrative hash):

```json
{"titular_check":{"status":"AVAILABLE","response_hash":"0xaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","url":"/titular-check/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa-prama-dynamagh"}}
```

Clients resolve the relative URL against the **public frontend HTTPS origin**,
not an internal API/Gateway host. For example:

```text
PRAMA verification: PERMIT
Titular Check:
https://prama-dynamagh.up.railway.app/titular-check/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa-prama-dynamagh
```

After actually rendering the link, acknowledge presentation with the existing M2M
Bearer at `POST /v1/m2m/titular-check/presented`:

```json
{
  "response_hash":"0xaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "url":"/titular-check/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa-prama-dynamagh",
  "presentation_context":"interaction-local-reference"
}
```

The URL is mandatory to audit preservation; it must exactly equal the returned
relative URL. Only a digest of presentation_context is retained. Optional
`presented_at` is client-reported metadata; server receipt time determines latency
and the deadline, so backdating cannot improve the score. This endpoint is an
agent's contractual assertion, not proof that a person saw anything.

The current shared Bearer establishes a context, not necessarily one identity.
Presentation requires exactly one active EXTERNAL_API_AGENT in that context, and
the persisted Ticket/mandate must belong to that identity and context. No supplied
agent ID is accepted. `DISCLOSURE_AGENT_CONTEXT_AMBIGUOUS` rejects before attribution
or any event/score mutation. Separately authenticating multiple agents requires
an identity-scoped credential contract; v0 does not pretend the shared token does
that. Unknown/foreign hashes and altered URLs are rejected with idempotent anomaly
events attributed only to the authenticated caller, never to the receipt owner.

## Persistence and event meanings

UsageEvent has the needed event ID, timestamp, lineage and JSON metadata. No new
table is needed. Migration `0021_titular_disclosure` protects these records with
PostgreSQL triggers: UPDATE/DELETE of disclosure records and TRUNCATE of a table
containing them fail. This is database enforcement, not merely absent edit routes.
Migration must precede API/worker deployment. No destructive downgrade is supplied.

Metadata contains the event type, response hash, internal Ticket/mandate/run/agent
identity where available, server timestamp, source, request ID, minimal metadata,
schema version and canonical event hash. This separate audit hash does not replace
the response hash. Replay validates the event hash and its column/metadata binding.

| Event | What it establishes | Idempotence |
| --- | --- | --- |
| TITULAR_CHECK_ISSUED | Ticket exists and its receipt URL can be constructed | One canonical response hash |
| TITULAR_CHECK_DELIVERED_TO_AGENT | Successful final ASGI body send of the M2M contract | One logical response hash/context delivery |
| TITULAR_CHECK_PRESENTED_BY_AGENT | Agent asserts it rendered the exact receipt link after delivery | One identity/response hash |
| HUMAN_PRESENCE_VERIFIED | Server accepted a receipt-bound Turnstile challenge | One access session |
| TITULAR_CHECK_OPENED_BY_TITULAR | Gated session loaded the safe receipt | One per access session; multiple sessions allowed |
| TITULAR_CHECK_VERIFIED_BY_TITULAR | Gated loading/reverification met the verification predicates | Unique server request ID per verification |
| TITULAR_CHECK_ACKNOWLEDGED_BY_TITULAR | Explicit acknowledgement after loading | One receipt-bound session |
| TITULAR_CHECK_PRESENTATION_INVALID | Rejected hash/URL/lineage/order assertion | Caller/hash/reason |

Event IDs for logical operations use deterministic UUIDs plus the existing primary
key and INSERT ON CONFLICT DO NOTHING. Concurrent retries cannot overwrite events.
Public locators still use response hashes, never these internal event IDs.

Delivery means the server transport accepted the completed response, not that the
agent rendered it. Socket delivery and database commit cannot be atomic: if audit
storage fails after sending, `TITULAR_CHECK_DELIVERY_AUDIT_UNAVAILABLE` is logged
without secrets; delivery remains unproven until a successful retry. A failed body
send never creates DELIVERED. Historical Tickets are observed lazily when first
delivered/accessed; no historical delivery or human interaction is fabricated.

## Human presence and deployment

The frontend first displays only the receipt shell. It reads
`GET /v1/titular-check/config`, renders Turnstile, and posts the ephemeral token to
`POST /v1/titular-check/{slug}/challenge`. Server-side Siteverify checks success,
allowed hostname, action `titular_check`, and cdata equal to the path hash. Token
validation is single-use and server-side as required by
[Cloudflare Siteverify](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).
The widget uses [explicit rendering](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/).

The validated browser receives a signed grant scoped to response hash, session,
IP HMAC and user-agent hash, expiring in 15 minutes. It is kept in component memory,
not localStorage, URLs or cookies. Only then can
`GET /v1/titular-check/{slug}` return the safe receipt. Simple crawlers/GETs cannot
create OPENED. CAPTCHA attests presence heuristically; it is not legal identity or
proof that the visitor is the actual authority holder. The event metadata states
`HUMAN_PRESENCE_ONLY`. Possessing the hash cannot expand safe-share data.

VERIFY AGAIN uses only GET with the grant, reconstructing and replaying again. It
may append access/verification events but cannot issue domain artifacts or spend.
ACKNOWLEDGE is a separate POST to `/{slug}/acknowledge`, requires the gated session
to have loaded the receipt, and explicitly returns `action_approval: false`.

Create a Cloudflare Turnstile widget restricted to the public frontend hostname.
Configure these **API** environment variables on Railway through its secret UI:

| Variable | Contract |
| --- | --- |
| TURNSTILE_SITE_KEY | Public widget key |
| TURNSTILE_SECRET_KEY | Siteverify secret; API only |
| TITULAR_CHECK_SESSION_SECRET | Independent random signing/HMAC secret, at least 32 characters |
| TITULAR_CHECK_ALLOWED_HOSTS | Exact comma-separated public frontend hostnames |
| TITULAR_CHECK_PRESENTATION_DEADLINE_SECONDS | Default 30; 1–86400; persisted with first delivery |

The worker only needs the presentation deadline setting if configured; no
Turnstile secrets belong in the frontend build or Gateway. Missing configuration
fails closed with 503; there is no fake CAPTCHA fallback. POST origin must be
HTTPS and match an allowed hostname. The production widget has not been configured
or validated by the local test suite.

API responses and receipt HTML use `Cache-Control: no-store` and
`X-Robots-Tag: noindex, nofollow, noarchive`. Database rate limiting permits at most
60 attempts/IP-HMAC/minute and 120/response-hash/minute, serialized by PostgreSQL
advisory transaction locks. Only HMAC/hash identifiers enter events. The application
does not trust raw X-Forwarded-For. Deployment must restrict ASGI trusted proxies
and preserve the client address correctly; otherwise shared proxy addresses are
conservatively rate-limited together. Turnstile tokens and access grants are never
persisted in events. Infrastructure access-log retention is a separate deployment
setting, not a claim that all external logs were erased.

## DISCLOSURE_COMPLIANCE and longitudinal integration

Version: `titular-disclosure-v0`. `eligible` counts unique delivered response hashes.
Within the first delivery's persisted deadline, an unpresented receipt is
`awaiting_presentation`, not an immediate failure. `evaluated_eligible` counts
presented receipts plus expired outstanding receipts. The explicit grace policy is:

```text
compliant = evaluated receipts with a valid, canonical, on-time presentation
compliance = compliant / evaluated_eligible, or null if none are evaluated
after every deadline has elapsed: evaluated_eligible == eligible
presentation_missing_count = expired delivered receipts without presentation
```

Late presentations are recorded as late and remain noncompliant. Retries cannot
restart the deadline. OPENED/VERIFIED/ACKNOWLEDGED are separate principal-controlled
counters and have no weight in this formula. Invalid presentation attempts remain
auditable independently of eventual valid presentation. No LLM or Gamma input is
used. A fixed stream and explicit `as_of` reconstruct identical components/hash.

`build_o_agent_stream()` already includes UsageEvents. The additive
`build_o_agent_disclosure()` dimension exposes receipt counts, missing/late counts,
latency per receipt, preserved/mismatched hashes and URL counts, principal counters,
source event references and a deterministic projection hash without changing the
frozen o-agent-v0 schema. `build_disclosure_memory()` is its cumulative event-sourced
K-Mem projection: subsequent operations retain history through persisted events.
It does not claim to instantiate Kernel Xi or a preexisting K1/K-infinity class.

Authenticated `GET /v1/agent-identities/{agent_id}/disclosure?as_of=<ISO timestamp>`
exposes the O_AGENT/K-Mem dimension as `AVAILABLE_POLICY_SIGNAL` to G13/Golemsguard.
No safe enforcement hook currently exists for this dimension. G13 enforcement,
thresholds, Decision gate, PRAMA kernel, G12 and Telegraph routing remain unchanged.

## Validation

Use the dedicated disposable PostgreSQL database `prama_titular_test` on
`127.0.0.1:55439`; set `DATABASE_URL` and `TITULAR_TEST_DATABASE_URL` to its local
connection string, apply Alembic, then run `pytest tests/receipts -q`.
These tests use real database persistence and direct SQL mutation attempts.
They roll back fixtures and make no Telegraph/provider calls. The sole external
verification transport is simulated. `npm test`, `npm run test:browser` (local
Edge), `npm run typecheck`, and `npm run build` validate the frontend; browser
tests simulate API/Turnstile transport and inspect widths 360/390/430/1280.
